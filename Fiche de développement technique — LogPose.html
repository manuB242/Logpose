Fiche de développement technique — LogPose

Document complémentaire au cahier des charges. Objectif : cadrer les choix techniques pour l'implémentation des 9 écrans spécifiés (tableau de bord, filtres, catalogue métiers, fiche métier, orientation conversationnelle, recommandation de parcours, établissements, annales).

1. Architecture générale

┌─────────────────────┐        ┌──────────────────────┐        ┌────────────────────┐
│   Application mobile │  HTTPS │   API backend (REST   │        │   Base de données   │
│   (iOS / Android)     │◄──────►│   ou GraphQL)         │◄──────►│   relationnelle      │
└─────────────────────┘        └──────────┬───────────┘        └────────────────────┘
                                            │
                                            ▼
                                ┌──────────────────────┐
                                │  Service IA           │
                                │  (assistant d'orientation,
                                │   scoring de parcours) │
                                └──────────────────────┘
  • Client : application mobile consommant une API via HTTPS/JSON.
  • Backend : expose les données du marché de l'emploi, le catalogue métiers/établissements/annales, et orchestre l'assistant d'orientation.
  • Service IA : isolé du reste du backend (latence et coûts différents), appelé pour la conversation d'orientation (2.5) et le scoring de compatibilité profil/parcours (2.6).
  • Stockage fichiers : bucket objet (type S3-compatible) pour les PDF d'annales, séparé de la base relationnelle.

2. Stack proposée

Couche Choix proposé Justification
Application mobile Flutter ou React Native Un seul code pour iOS/Android ; équipe réduite. React Native consomme directement l'API REST PHP via HTTPS/JSON.
Gestion d'état Riverpod (Flutter) ou Redux Toolkit / Zustand (RN) Prévisibilité des filtres combinés (zone, secteur, entreprise, type d'emploi) partagés entre écrans.
Backend API PHP 8 natif (sans framework) API REST légère, déployable sur des hébergements PHP standards ; routage explicite et requêtes PDO préparées, sans dépendance de framework.
Base de données PostgreSQL Données structurées et relationnelles (secteurs, métiers, établissements, concours) ; bon support des agrégations pour le tableau de bord.
Cache Redis Résultats du tableau de bord (agrégats par période/filtres) coûteux à recalculer à chaque appel.
Stockage fichiers S3-compatible (ex. Scaleway, OVH, ou AWS S3) Hébergement des PDF d'annales, faible coût, CDN possible.
Assistant d'orientation Appel à un modèle de langage via API (ex. Claude) avec prompt système dédié Pas d'entraînement de modèle propriétaire nécessaire au démarrage.
Authentification JWT + refresh token Standard, compatible mobile.

Ces choix sont des recommandations de départ, à valider selon les compétences disponibles dans l'équipe et les contraintes d'hébergement au Congo (connectivité, coût data).

5. Points d'attention techniques

  • Agrégations du tableau de bord : précalculer/cacher (Redis) les combinaisons de filtres les plus fréquentes ; éviter de recalculer les pourcentages sectoriels à chaque requête si le volume de IndicateurEmploi devient important.
  • Paramètre n (top métiers) : borné côté API (ex. max 50) pour éviter des payloads excessifs.
  • Service IA (2.5/2.6) : conserver l'historique de conversation côté serveur (pas uniquement client) pour permettre la reprise de session et l'audit des recommandations ; définir un prompt système strict pour limiter les dérives hors sujet orientation.
  • Téléchargement des annales : utiliser des URLs signées à durée limitée plutôt que des liens publics permanents vers le bucket.
  • Connectivité limitée : prévoir un mode cache local (dernier tableau de bord chargé, dernières fiches métiers consultées) pour un usage en connexion intermittente.
  • Confidentialité : les échanges de la conversation d'orientation (2.5) contiennent des données personnelles sensibles au sens du cahier des charges (§3.5) — chiffrement au repos et politique de rétention à définir.
